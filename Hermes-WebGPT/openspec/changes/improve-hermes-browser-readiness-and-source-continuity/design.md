# Design — готовность браузера, сохранение источников и наблюдение задержек

## Границы и существующие владельцы

Изменение расширяет три существующих компонента Hermes-WebGPT. Решение повторного
использования: **EXTEND_CANONICAL_OWNER** для `hermes_windows_browser`,
`model_news_prefetch` и `monitoring.queue_monitor`. Новый транспорт, Gateway,
координатор очереди и ledger доставки здесь не создаются. Подключение плагинов,
параллельные потоки и исправление DOM-отправки выполняются в других участках;
эти файлы не перезаписываются данным изменением.

## FR-001–003: запуск браузерного инструмента

`gateway_bootstrap.run()` вызывает `configure_browser_launcher()` перед штатным
`hermes_cli.gateway.run_gateway`. Совместимость ограничена Windows x64 и известным
`node_modules/.bin/agent-browser` внутри обнаруженного Hermes source root.
`select_native_browser()` проверяет имя npm-пакета, существование native exe,
PE-сигнатуру, смещение заголовка и архитектуру. Чужие команды, неподходящие
платформы и неисправные пакеты сохраняют исходное поведение. `npx`, shell и
установка пакетов не вызываются; аргументы пользователя не переписываются.

`find_existing_browser()` уважает явный `AGENT_BROWSER_EXECUTABLE_PATH`. При его
отсутствии проверяются установленные Chrome и Edge в стандартных абсолютных
каталогах. Наличие exe не доказывает успешную навигацию. Bootstrap атомарно
сохраняет PID, время и SHA загруженных helper/bootstrap в
`gateway_browser_runtime.json` до передачи управления тому же Gateway.
Сам receipt без проверки живого процесса не считается текущей активацией.

Исходники, CLI readiness, навигация, активированный Gateway и Telegram ACK —
отдельные уровни доказательств. Unit-тест bootstrap подменяет Gateway и не
запускает реальный процесс. Полная повторная приёмка FR-003 остаётся открытой:
в этом запуске Gateway и браузер не перезапускались, сообщений не отправляли.

## FR-004–006: сохранение публичных источников

`maybe_prefetch_news()` использует существующий ограниченный сбор RSS.
Первичный ход пользователя может инициировать сбор; ход с результатом инструмента
только читает cache. Ключ — SHA-256 точного последнего сообщения пользователя;
в cache хранится публичное evidence, а не исходный приватный текст.
`_remember_turn()` / `_reuse_turn()` используют lock, defensive copy,
монотонный TTL 300 секунд и максимум 12 записей. Чтение не продлевает TTL,
откат часов и истечение удаляют запись. Другая задача не наследует evidence.

Промах на tool-followup не запускает сетевой запрос. Ограничения источника,
headline-only provenance и отсутствие результатов сохраняются. Canonical
messages, реальные tool results, tool_choice и схемы инструментов не меняются.
Сбор ограничен четырьмя daemon fetch, бюджетом ожидания 1.2 секунды и тайм-аутом
источника 3.5 секунды; медленный DNS может пережить его, но не создаёт
неограниченное число потоков. Эти параметры существующего сборщика не менялись.
Цель ускорения — убрать повторный fetch между ходами одной задачи, а не обещать
фиксированное время ответа модели.

## FR-007–009: наблюдение существующей очереди

`queue_monitor.read_metadata()` открывает существующую SQLite через `mode=ro`,
включает query_only и выбирает только id/state/reason/created. Payload, result,
lease и URL не читаются. Идентификатор хешируется; причина выдаётся только из
фиксированного каталога, неизвестное значение становится `other`.

Каталог v3 добавляет подтверждённые исходниками коды, включая
`user_message_not_confirmed`, `assistant_timeout` и ошибки binding/recovery.
Наблюдавшиеся служебные `reasoning_control_not_unique` и
`owner_cancelled_stale_unsent` также имеют фиксированные безопасные метки.
Каталоги v1/v2 сохраняются отдельно. Старый snapshot не может приписать себе
код, которого в его версии ещё не было. Замена старого `other` новым кодом
отмечается как уточнение только для той же записи и того же состояния, когда
код отсутствовал в старом каталоге. Новая запись, переход active → failure,
смена уже известной причины или смена причины внутри v3 остаются тревогой.

Latency target по возрасту создания запроса отделён от stale threshold.
Значения по умолчанию: stale 600 секунд, окно исходов 3600 секунд; driver задаёт
целевой возраст 120 секунд. Это не длительность текущей фазы. Окно строится
по времени создания; completion ratio относится только к inference и равен
unknown при отсутствии terminal observations. Relay done не доказывает
Telegram ACK или корректность ответа.

`queue_monitor_baseline --check` не изменяет baseline. Режим
`--advance-if-clean` не подтверждает новые ошибки автоматически. Обновление v3
не меняет очередь, не разрешает повтор Send и не объявляет инцидент решённым.

## Альтернативы

- Переустановка Hermes/браузера вместо узкой совместимости добавляет зависимости
  и меняет окружение пользователя; выбран существующий native exe.
- Повторный web fetch на каждом tool turn увеличивает задержки и теряет
  происхождение evidence; выбран bounded cache публичных данных.
- Произвольные строки причин из БД раскрывают пользовательские данные;
  выбран версионированный фиксированный каталог.
- Новый монитор или ledger дублирует действующего владельца. Сохранены
  существующие CLI, baseline driver и контракт ошибок.

## Применение и откат

Источник монитора заменён по SHA/CAS после успешных candidate-тестов.
Исходный файл сохранён без преобразования байтов в
`planning/response-quality-completion-20261111/queue_monitor.before.py`.
Helper браузера, news cache и bootstrap в этом запуске не менялись.
Перезапуск Gateway/Relay для чтения нового монитора не нужен.

При откате сверить текущий SHA и восстановить только принадлежащий изменению
код. Не восстанавливать SQLite очереди, не переотправлять сообщения и не
сбрасывать baseline для устранения тревоги. Старый монитор v2 не читает snapshot
v3: если baseline уже был легально продвинут, требуется совместимый reader либо
явный статус unavailable до проверки владельцем; скрыто понижать baseline нельзя.

## Проверка и ограничения

`docs/RESPONSE_QUALITY_COMPLETION_20261111.md` содержит свежие SHA, реальные jobs,
FR/test crosswalk и текущие результаты. Из 114 Windows-тестов 113 прошли,
один symlink-тест пропущен из-за прав ОС. Проверки используют временные fixtures
и текущие production-модули; это не новый Telegram E2E. Сильная OS identity,
аутентификация MCP host и защита от злонамеренного процесса того же пользователя
остаются отдельными механизмами.
