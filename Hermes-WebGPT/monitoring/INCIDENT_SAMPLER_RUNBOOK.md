# Hermes incident sampler — безопасная локальная диагностика (не активирована)

## Назначение

incident_sampler.py делает **явный** read-only опрос существующего Relay SQLite через monitoring/queue_monitor.py и пропускает его очищенный JSON через incident_triage.py. В отдельном локальном SQLite-журнале сохраняются baseline и краткое наблюдение **в одной BEGIN IMMEDIATE → COMMIT транзакции**. Relay, браузер, Gateway, Telegram и host approval никогда не меняются. Ни одна неопределённая отправка не повторяется. Для работы не требуются сетевые запросы или аккаунт GPT.

Скрипт в GitHub PR #13 **не установлен и не запущен** на пользовательском Windows ПК. Local Workspace MCP сейчас отвечает Session terminated; это значит «данные недоступны», не подтверждённую остановку агентов.

## Одна проверка (PowerShell, после сверки исходника и фактического пути)

Из корня проверенного Tunnel checkout с Python 3.10+; два пути ниже — **плейсхолдеры**, они НЕ обозначают обнаруженные файлы:

    py -3 Hermes-WebGPT\monitoring\incident_sampler.py --db "C:\PATH\TO\ACTUAL\relay.sqlite" --journal "C:\PRIVATE\HermesObservations\incident-journal.sqlite" --stale-seconds 600 --latency-target-seconds 120

Реальный путь Relay SQLite берётся из текущей конфигурации его запуска. Журнал должен быть другим локальным файлом, в приватном каталоге владельца, без облачной/общей сетевой публикации. Не используйте папку репозитория или публичный Obsidian как хранилище приватной истории. Сам скрипт создаст каталог/SQLite при наличии файловых прав, но не создаёт отсутствующую базу Relay.

Для **добровольного** непрерывного наблюдения в текущем foreground-окне:

    py -3 Hermes-WebGPT\monitoring\incident_sampler.py --db "C:\PATH\TO\ACTUAL\relay.sqlite" --journal "C:\PRIVATE\HermesObservations\incident-journal.sqlite" --interval 60

Останавливается Ctrl+C. Это **не** служба, не scheduler и не дистанционная автоматизация. Мониторинг прекращается с завершением процесса/ПК. Не запускать для живой системы до проверки версии исходников, Python, схемы Relay, прав и действующего инструмента approval.

## Что записывается

В файле журнала две таблицы: monitor_baseline (одна предыдущая очищенная snapshot запись) и incident_events (время + санитизированная категория, счётчики, уверенность и разрешённый безопасный следующий шаг). По умолчанию сохраняются максимум последние **2000** записей событий, настраивается через --keep-events. Baseline содержит хешированные request ID, состояния/коды причин и timestamp, но никогда не содержит prompt, result, URL, cookie, tool arguments, Telegram токен или CDP endpoint.

Сами SQLite journal/backup могут сохранять прежние страницы после удаления логических записей до VACUUM; retention **не гарантия мгновенного физического стирания**. Используйте приватную файловую систему, защищённую копию и политику удаления всего файла. Встроенная SHA-256 идентичность request ID может коррелировать с повторными snapshot; не публиковать журнал.

Ошибочный/недоступный источник фиксируется как observation_unavailable; старый корректный baseline НЕ стирается. Ошибка чтения или повреждения самого baseline не приводит к его молчаливой замене. Перезапуск после потери соединения сам по себе не означает, что ранее неизвестная внешняя отправка не была выполнена.

## Коды завершения для одного опроса

0 — монитор прочёл очередь, нет известных причин внимания **в наблюдаемой области**. Не подтверждает здоровье браузера, качество ответа, готовность Gateway или фактическую доставку Telegram.

1 — очередь доступна, обнаружена проблема (включая исторические uncertain). Требуется расследование, повтор Send запрещён.

2 — данных/журнала или схемы недостаточно. «Наблюдение недоступно», а не «все агенты остановлены».

Режим --interval повторяет проверки в foreground, печатает очищенный JSON после каждой, завершается по Ctrl+C (130).

## Проверка перед передачей другим агентам

- Исходная база никогда не открывается на запись, journal DB отличается от неё даже после path.resolve; symlink target отклоняется.
- Параллельные экземпляры сериализуют состояние через SQLite BEGIN IMMEDIATE; baseline и запись инцидента атомарны.
- При падении до commit предыдущий baseline сохранён. После commit оба соответствующих поля видны согласованно.
- Ограничены размеры snapshot/incident, лимиты строк и retention; без network/model.
- Проведены синтетические regression: 16 sampler + 29 causal triage, включая 24 конкурентных цикла, invalid/corrupt baseline, outage, no secrets, rollback. Эти тесты не являются реальным Windows/GPT/Telegram E2E.
- Требуются отдельно smoke полного существующего monitor suite на настоящей Windows версии и верификация скачанных/загруженных Git SHA.

## Недостатки текущего этапа

Сведения только по queued/claimed/intent/saved/done/blocked/uncertain, created timestamp и reason. Нет независимых heartbeats реального worker, фазовых p50/p95, аутентифицированных event producer, provider receipts и единого distributed trace. Это направление следующего этапа через scoped collector и Autopilot ledger; до него любой статус остаётся reported_only / queue_metadata_only.
