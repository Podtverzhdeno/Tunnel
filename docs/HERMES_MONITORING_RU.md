# Hermes: наблюдение очереди и ускорение

## Что проверено 10 ноября 2026

Плановый монитор включён и проверяет Hermes примерно раз в час. Последний
доступный результат проверки завершён 10.11.2026 в 15:20:49 UTC:
Local Workspace вернул `Session terminated`, диагностические скрипты на Windows
не запускались. Повторная проверка подключения в рабочем чате дала ту же ошибку.
Это означает отсутствие свежего наблюдения, а не подтверждённую остановку Hermes.

На предоставленном пользователем снимке Telegram видны `web_manual_input` и
`web_uncertain_send`. Текущая очередь, активный запрос и состояние поля ChatGPT
не прочитаны. Причина `manual_input` может быть как ручным текстом, так и
неубранным собственным черновиком; по одному коду это установить нельзя.

Новая диагностика опубликована в GitHub отдельно от живой Windows-установки.
Текущие локальные изменения Hermes и Web Companion из-за разрыва соединения
не получены и этим коммитом не синхронизированы. Переносимые ZIP от 4 ноября
не пересобирались; они не содержат эту диагностику.

## Read-only диагностика очереди

`Hermes-WebGPT/monitoring/queue_monitor.py` — независимый Python 3.10+ скрипт
без сторонних зависимостей. Он не импортирует Relay, не запускает браузер,
не отправляет запросы модели, не меняет состояния и не повторяет Send.

Совместимость проверена с сохранённой схемой Relay: таблица `requests`,
колонки `id`, `state`, `reason`, `created`. Перед подключением к действующей
установке необходимо подтвердить её текущую схему и реальный путь SQLite.
Путь определяется конфигурацией запуска Relay, а не угадывается по имени.

Читаются только четыре перечисленные колонки. `payload`, `result`, `lease`,
`worker` и URL не выбираются. Идентификатор превращается в SHA-256, причины
приводятся к фиксированному списку; произвольный текст причины не выводится.
Полный JSON-отчёт остаётся локальной диагностикой, его не следует коммитить.

Открытие SQLite использует `mode=ro` и `query_only`; отсутствующая база не
создаётся. `immutable=1` не применяется, чтобы учитывать committed-записи WAL.
SQLite может использовать вспомогательные WAL/SHM-файлы; код не изменяет
содержимое таблиц и не выполняет миграции. Лимит строк проверяется явно;
превышение лимита означает недоступное наблюдение, а не частичный «успех».

Из корня репозитория, подставив существующий путь:

```powershell
py -3 Hermes-WebGPT\monitoring\queue_monitor.py --db "C:\path\to\relay.sqlite"
```

Коды завершения:

| Код | Значение |
|---|---|
| 0 | Метаданные прочитаны; новых ошибок и старых активных запросов не обнаружено |
| 1 | Требуется внимание: новая ошибка, зависание или история ошибок без baseline |
| 2 | Наблюдение недоступно: файл, схема, baseline, часы или лимиты не подходят |

Код 0 не подтверждает соединение Telegram, живой Gateway, работоспособность
расширения или доставку ответа. Поле `scope=queue_metadata_only` ограничивает
смысл результата.

Для сравнения сохраните полный успешный отчёт в закрытой локальной папке и
передайте его следующим запуском через `--baseline`:

```powershell
py -3 Hermes-WebGPT\monitoring\queue_monitor.py --db "C:\path\to\relay.sqlite" --baseline "C:\private\previous-report.json"
```

Скрипт сам не пишет baseline. Потребитель должен атомарно сохранять stdout
после проверки `observation=available` и exit code 0 или 1. При exit code 2
оставить прежний baseline. Нельзя направлять stdout поверх файла, который
тот же процесс читает через `--baseline`: shell может обнулить его до чтения.

Без baseline обнаруженная история ошибок помечается как история с неизвестной
новизной. При наличии baseline сравниваются состояния и причины по каждому
хешу запроса, поэтому одинаковое суммарное число `blocked` не скрывает новую
ошибку. Изменившаяся идентичность базы или исчезнувшие записи требуют явного
нового baseline; скрипт не считает такую смену нормальной проверкой.

Активные `queued`, `claimed`, `intent`, `saved` старше 600 секунд требуют
внимания. Порог меняется через `--stale-seconds`. Это возраст от `created`,
включающий всё ожидание запроса, а не длительность текущей стадии. В
сохранённой схеме нет достаточных меток для расчёта p50/p95 каждой стадии.

## Что проверять после восстановления подключения

1. Прочитать статус Gateway, HTTP health Relay и последнюю собственную запись
   очереди. Запустить существующие `diagnose_live_oneshot_20261109.py` и
   `diagnose_relay_failures_readonly_20261110.py`, дождаться exit code и stdout.
2. Сравнить SHA исходников с установленным расширением и фактической версией
   работающего service worker. Совпадение файлов не доказывает, что браузер
   уже загрузил новый код.
3. Для `manual_input` только наблюдать собственную вкладку и принадлежность
   черновика. Ручной текст сохранить; автоочистка всех полей недопустима.
4. Для `uncertain_send` сначала найти подтверждение сохранённого сообщения и
   результата того же запроса. Переключение транспорта или повторный Send
   без разрешения неопределённости запрещены.
5. Провести один новый разрешённый тест Telegram → Hermes → веб ChatGPT →
   Hermes → Telegram с уникальной меткой и сквозным request ID. Отдельно
   проверить обычный ответ, вызов инструмента и продолжение после инструмента.
6. Уведомлять и о потере самого наблюдения. Отсутствие доступа должно быть
   обозначено как отсутствие данных; исторические ошибки не выдавать за новые.

В группе проверяются privacy mode, упоминание бота, права отправки и allowlist
отправителя. `/sethome` выбирает канал фоновых результатов, но сам по себе
не исправляет передачу обычного сообщения в модель.

## Измерение и план ускорения

Сначала добавить в существующий Relay/worker метки событий без текстов и
секретов: `enqueued`, `claimed`, `content_ready`, `send_intent`,
`message_saved`, `answer_ready`, `hermes_received`, `telegram_delivered`.
Для интервалов одного процесса использовать монотонные часы. Для разных
процессов — согласованные UTC-метки с явной оценкой расхождения часов.
Успешный HTTP-ответ провайдера не равен доставке в Telegram.

| Интервал | Возможное изменение | Условие проверки |
|---|---|---|
| enqueued → claimed | Немедленный poll при явном запуске и завершении предыдущего задания; короткий poll только пока есть работа | Один claim на запрос; не менять Send и ownership |
| claimed → content_ready | Ограниченный bootstrap в том же `documentId`, повторная проверка уже запущенного runner | Потерянный ACK не создаёт второй runner и не повторяет отправку |
| content_ready → message_saved | Проверка готовности редактора событиями с резервным таймером | Подтверждённое сообщение с тем же request ID; ручной текст сохранён |
| message_saved → answer_ready | Ожидание DOM-событий с финальной проверкой завершения | Частичный ответ и исчезнувшая кнопка не считаются готовым результатом |
| hermes_received → telegram_delivered | Измерить обработку tool calls и фактическую отправку Telegram | Не путать размышление, tool call и финальный ответ |

В сохранённой версии Relay `claim` допускает только один запрос в
`claimed/intent/saved` одновременно для всех транспортов. Это возможная
причина очереди, но не подтверждённая характеристика текущего процесса.
Не увеличивать concurrency до доказанной независимости ownership, вкладок и
результатов. Изменение таймаутов не устраняет очередь и может увеличить
`uncertain_send`.

Затем уменьшать повторяющиеся описания навыков/инструментов и ограничивать
вывод инструментов до отправки в веб. Не удалять system-инструкции и пары
tool-call/tool-result. Для данной установки Hermes требуется заявленный
контекст не ниже 64K; уменьшение `model.context_length` до 30K уже вызывало
отказ. Флаг `compression.enabled` не доказывает, что компрессор реально
работает в памяти Gateway. Бюджет символов Relay и токены модели — разные
величины.

Приёмка ускорения: сравнить p50/p95 стадий на последовательных новых запросах
до/после изменения, отдельно учитывать холодный запуск, очередь и tool calls.
Нельзя публиковать процент ускорения без этих замеров. Обязательные сценарии:
ручной текст, потерянный ACK, навигация вкладки, пауза пользователя, ошибка
модели, большой контекст, неизвестный Send и потеря соединения Telegram.

## Проверка опубликованного кода

```powershell
py -3 -m unittest discover -s Hermes-WebGPT/monitoring -p "test_*.py" -v
```

Проверены 26 тестов на синтетической SQLite, включая WAL, неизменность
содержимого базы, отсутствие секретных колонок в SELECT, новые/старые ошибки,
смену базы, пороги, malformed baseline и коды завершения. Это проверка
диагностического кода, а не новая E2E-проверка Telegram или установка на Windows.

## Обновление после восстановления доступа, 10.11.2026

Доступ к Windows восстановился. В 16:24 UTC штатная диагностика показала
Gateway running / Telegram connected по state-файлу, Relay HTTP 200,
19 done, 19 blocked, 2 uncertain, без активных записей. Два новых запроса имеют
сохранённое сообщение и результат; их доставка в Telegram отдельно не проверена.
Старый uncertain/request_timeout не повторялся и не сбрасывался.

На ПК добавлен опубликованный queue_monitor и выполнены его 26 тестов на
Windows. Исправлена переносимость самих тестов: убран запрещённый в Windows
символ вопросительного знака из имени fixture; соединения SQLite явно
закрываются до удаления временных файлов. Это не изменение схемы живой базы.
Первый live запуск вернул observation=available и exit 1 из-за существующей
истории ошибок без baseline, как и предусмотрено контрактом; новый queued
был моложе порога зависания.

В существующий Web Companion через SHA CAS внесено [ускорение следующего
запроса и защита от гонок завершения](../Hermes-WebGPT/patches/queue-latency-20261110/README.md).
Подтверждены source/install MATCHED и PUBLISHED. Загрузка новой ревизии в
пользовательском браузере отдельно не подтверждена; принудительный reload
при неопределённой работе не выполнялся.

Существующий почасовой монитор уточнён без изменения расписания: сообщать о
каждом новом manual_input/uncertain_send/request_timeout, включать saved в
проверку зависания, отличать exit 1 диагностического контракта от недоступности
наблюдения и сохранять явное UNKNOWN для доставки и загруженной ревизии.

Параллельно наблюдён другой relay.py SHA b7da8c8bfdee с импортом проверки схем
инструментов. Этот файл данной правкой не изменялся; версия файла не доказывает
версию кода в уже работающем процессе.
